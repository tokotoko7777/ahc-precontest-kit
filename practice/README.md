# 手法別の実戦例とスコア回帰

全AHCを網羅することは目標にしません。**共通フォーマットを使い、その手法の強さと
高速化を実問題のスコアで確認できる問題**を重点的に整備します。
既存の他問題は参照用として残しますが、全件の継続強化は必須にしません。

| 主な手法 | 重点問題 | 問題側の編集箇所がまとまった原本 |
|---|---|---|
| 焼きなまし・途中再生 | AHC058 | [購入順序SA](../examples/search/ahc058_prefix_sa.cpp) |
| 焼きなまし・閾値打ち切り | AHC001 | [領域再構築SA](../examples/search/ahc001_region_sa.cpp) |
| 差分Actionビーム | AHC032 | [Mod Stamp](../examples/search/ahc032_action_beam.cpp) |
| apply/revert木上ビーム | AHC021 | [Pyramid Sorting](../examples/search/ahc021_tree_beam.cpp) |
| 世代が飛ぶ木上ビーム | AHC038 | [Tree Robot Arm](../examples/search/ahc038_variable_cost_beam.cpp) |
| Monte Carlo | AHC015 | [共通未来rollout](../examples/search/ahc015_common_rollout.cpp) |

表は整備・比較の優先対象であり、全方式の最新高速化が完了したという意味ではありません。
提出用`main.cpp`と原本の一致を自動検査しているのは、現在AHC001・032・058です。
他の例も、その手法の比較を進める際に整合性と公式スコアを確認します。

## 高速化の採用条件

1. ライブラリだけを変え、同じ探索量で出力・得点・同点時の順序が保たれるかを確認する。
2. 実問題で時間に余裕ができたら、同じ時間制限内で幅・試行数・sample数を増やす。
3. **問題本来のスコア**を主指標に、開発用入力で比較する。
4. 設定を固定した後、別の入力でも得点改善と時間内完走を確認する。
5. 生スコア・入力/出力/ソースのhash・幅・コンパイル条件・実時間を残す。

処理回数や合成ベンチの速さだけでは「強くなった」としません。微小な時間差だけで
採用せず、時間超過した設定の高得点も採用理由にしません。時間は環境依存なので、
手元での完走をAtCoderのTLE保証と扱わないでください。

手法をまたいでスコアを合算しません。同じ問題の比較では全版共通のケース別bestを
分母とする比率も併記します。公式順位とは別物です。
