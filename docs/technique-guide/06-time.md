# 6. 時間予算

[目次へ](README.md) · [前：乱数と再現性](05-randomness.md) · [次：検証と実験](07-validation.md)

探索を速くしても、答えの復元と出力が間に合わなければ使えません。時間を探索だけの資源と考えず、プログラム全体で配分します。

<a id="b24"></a>
## B24. 探索の締切と出力の締切を分ける

総予算から、答えの復元・検査・出力に必要な時間を先に引きます。残りが探索に使える時間です。

例えば総予算2秒、終了処理の余白0.05秒なら、探索を1.95秒で終える設計にします。終わってから最良解を復元し、必要な形式へ変換して出力します。探索を2秒まで回してしまうと、その後の処理時間を確保できません。

余白は、入力の大きさや答えの長さによって変わります。短い入力で必要だった時間だけを基準にせず、終了処理が重いケースでも測ります。

**注意。** `Timer` の起点は構築時です。入力や大きな前計算の後で作れば、その前の費用を数えていません。プログラム全体の制限を管理するなら、起点をどこに置くかを決めます。また、時計を読む間隔が粗ければ探索の終了判定も遅れます。

**練習。** 入力0.03秒、前計算0.20秒、探索1.70秒、終了処理0.08秒を使うプログラムについて、合計を求めて2秒以内に収める配分を考えてください。

**キットとの対応。** [Timer::is_over(limit_ms)](../../library/timer.hpp)。単位はミリ秒です。総予算2000 msから余白50 msを引き、`timer.is_over(1950.0)` で探索の締切を判定します。余白は利用者側で決めます。

<a id="b25"></a>
## B25. 時計を毎回読まず、間引いて確認する

1回の探索処理が短いと、毎回の時計呼び出しが無視できない費用になります。例えば256反復ごとに時刻を確認し、それまでは前回の判定結果を使う方法があります。

1反復が最大2マイクロ秒程度なら、確認間隔256回の仕事量は約0.512ミリ秒です。この遅れを終了余白と比べ、許容できるか判断します。1反復が急に10ミリ秒になる処理では、同じ間隔は大きすぎます。

**注意。** 間引きによって古くなるのは、終了判定だけではありません。温度を時間進捗から求めていれば、その進捗も段階的に更新されます。また、外側で1回 `is_over()` した後に長い内側ループへ入るなら、内側にも確認が必要です。

キットの `BatchedTimer` は最初の `is_over()` で確認し、その後は指定間隔で更新します。`cached_progress()` は最後に確認した進捗を返し、時計を読みません。`elapsed_ms()` は時計を読みますが、終了判定のキャッシュを更新する処理ではありません。

**練習。** 1反復の最長時間が0.1ミリ秒、許容したい確認遅れが5ミリ秒なら、何反復以下の間隔を目安にするか計算してください。OSによる中断などは別に余裕を取ります。

**キットとの対応。** [BatchedTimer(limit_ms, check_interval)](../../library/batched-timer.hpp) の `is_over()`、`cached_progress()`。

<a id="b26"></a>
## B26. 全体の時間軸でフェーズを管理する

探索が初期解生成・改善・最終修復の3段階に分かれているなら、それぞれの終了時刻を全体の時間軸上に置きます。

例えば探索予算1.8秒を、初期解0.2秒、改善1.4秒、修復0.2秒に分けるなら、終了時刻の目標は0.2秒、1.6秒、1.8秒です。各段階の開始時に毎回「1.8秒のタイマー」を作ると、合計予算を超えてしまいます。

段階ごとの進捗が欲しい場合は、全体の経過時間からその段階の開始時刻を引き、段階の予算で割ります。全体進捗をそのまま渡すと、2番目の段階がすでに進んだ温度から始まることがあります。

**注意。** 前の段階が予定を超過した場合に、後の段階へ最低限どれだけ残すかも決めます。必須の修復を最後に残すなら、改善がその予算を使い切らないようにします。

**練習。** 初期解が予定の0.2秒ではなく0.35秒かかった場合、修復に0.2秒残すには改善をいつ終える必要があるか求めてください。

**キットとの対応。** 1つの `Timer` から経過時間を読み、段階ごとの締切は利用者側で管理します。

<a id="b27"></a>
## B27. 残り時間から探索量を調節する

候補幅や反復回数を固定すると、軽い入力では余り、重い入力では間に合わないことがあります。直近の処理時間を測り、残り時間から次に使う探索量を見積もる方法があります。

例えば直近100候補に10ミリ秒かかり、残りが50ミリ秒なら、同じ費用が続くという仮定では約500候補を処理できます。変動と終了余白を考え、これより少なく計画します。

ここで重要なのは仮定です。候補数に比例しない処理、状態が大きくなる処理、入力で探索分岐が増える処理では、そのまま比例計算できません。小さな区切りごとに見積もりを更新します。

**注意。** 平均費用だけで締切を保証できません。重い1候補が残り時間を使い切る場合、途中で打ち切れる設計か、最悪費用を見込んだ開始判断が必要です。

**練習。** 候補幅を2倍にすると、並べ替え・状態コピー・評価の費用がそれぞれどう増えそうか考えてください。すべてが正確に2倍になるとは限らない理由を説明します。

**キットとの対応。** `Timer::remaining_ms(limit_ms)` で残量をミリ秒単位で取得します。幅の変更や早期終了は探索側で実装します。
