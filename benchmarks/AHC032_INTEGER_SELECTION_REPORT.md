# 整数scoreのヒストグラム選抜：不採用の記録

2026-09-17。[AHC032 Mod Stamp](https://atcoder.jp/contests/ahc032/tasks/ahc032_a)で
共通 `ActionBeamSearch` の上位候補選抜を試した。**score改善を確認できず、採用・マージしない。**
問題側の候補・評価・手数配分は変えていない。新しいTODOや設定項目も追加しない試作である。

## 試した処理

小さいtrivialな候補かつ64 bit以下の整数Scoreの場合、候補が1024件以上あれば次を行う。

1. 符号と最大化/最小化を考慮し、比較順を保つunsigned整数キーへ変換する。
2. キーの最小・最大で異なる上位8 bitを使い、256組の件数を数える。
3. 上位N件の境界が入る組だけを取り出し、その組の中を `nth_element` で選抜する。

最終的な順位・生成順による同点処理は変更しない。
全て同じscore、少数候補、浮動小数・独自Scoreでは従来の比較選抜を使う。
大きなActionや代入不能なActionは既存の候補ID選抜を維持する。
比較回数を減らせても、最小最大・度数集計・partitionの追加走査が必要で、必ず速くなるわけではない。

全20出力が合法で、公式Rust visualizerと独立した盤面再生のscoreが一致。

時間内の共通bestだけを全版共通の分母にし、2秒超過した当該版のケースは0点としている。

少なくともこの測定で「高速化→探索量増加→score改善」は示せなかった。
幅11000は両版とも時間超過があり、採用しない。設定を広く探して有利な結果だけを選ぶ追試も行っていない。

生データは [`ahc032-histogram-dev-5.csv`](results/ahc032-histogram-dev-5.csv)。
これは少数ケースの開発段階で落とした案であり、未使用入力での改善確認を終えた版ではない。
公式順位・上位者比との比較でもない。

## 検証・再現

`g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0`、
`-std=c++17 -O2 -DNDEBUG -Wall -Wextra -DAHC032_BEAM_WIDTH=<幅>`。
sourceはheader展開後の全文をhash化し、入力/出力hash、実時間、flags、比較元commitもCSVに保存する。
入力・配布ツールは同梱しない。手元の時間は提出環境を保証しない。

```sh
python3 benchmarks/ahc032_core_benchmark.py \
  --inputs /path/to/ahc032/tools/in --tool /path/to/ahc032/tools/target/release/vis \
  --reference-ref 8b79c5c30b5447a511bebeb2d55164bda8362887 \
  --reference-width 9000 --extra-reference-widths 11000 \
  --widths 9000 11000 --label histogram --cases 5 \
  --output build/ahc032-histogram-repeat.csv
```

全候補sortを正解とする複数世代のテストで、signed/unsigned 8〜64 bit、最小/最大値、
同点、正負の境界、最大化/最小化、少数/大幅、batched ON/OFFを確認する。
AHC032の単一提出ファイルも試作headerと同期するが、mainに採用済みの版とは区別する。

ローカルの `make verify` / `make verify-sanitize` は全て成功。
最初の全体検査は未コミットの部品を拒否するbundle検査で停止したため、
変更をコミットした後に全体を再実行した。
