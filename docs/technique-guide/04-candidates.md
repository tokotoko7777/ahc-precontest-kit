# 4. 候補の管理

[目次へ](README.md) · [前：差分更新と巻き戻し](03-incremental.md) · [次：乱数と再現性](05-randomness.md)

候補をたくさん作れるようになると、次は「どれを詳しく調べるか」「どれを残すか」が問題になります。探索の時間とメモリは有限なので、候補管理にも設計が必要です。

<a id="b16"></a>
## B16. Top-Kで残す候補数を制限する

Top-Kは、流れてくる候補のうち良いものを最大K個だけ残す仕組みです。候補を全部保存して並べ替える代わりに、残している候補の中の最悪と新しい候補を比べます。

得点 `4, 1, 9, 3, 7, 2` から上位3個を残すなら、最後は `9, 7, 4` です。3個埋まった後は、最悪の値より良い候補が来たときだけ入れ替えます。残す最悪を素早く取り出せるヒープを使えば、Kが2以上のとき、候補1件の挿入・入替えは最大 `O(log K)`、保持に必要な領域は `O(K)` です。

**注意。** 最大化と最小化を取り違えないことが重要です。キットの `TopK` は既定で大きい値を優先し、コンストラクタの第2引数を `false` にすると小さい値を優先します。保持中の要素は良い順に並び、空でなければ `entries.back().first` が最悪のスコアです。

同点の扱いも決めてください。全候補に通し番号を付け、得点が等しいときは番号で順序を決めると、再現性を持たせやすくなります。

**練習。** K=2で `5, 2, 8, 8, 1` を順に入れ、毎回残っている値と最悪値を書いてください。最大化と最小化の両方で試します。

**キットとの対応。** [TopK<Score, State>](../../library/top-k.hpp)。Kは正の整数が必要です。現行部品は小さいK向けの整列配列で、追加1回はO(K)です。上で述べたヒープ版のO(log K)とは実装が異なります。

<a id="b17"></a>
## B17. 代理評価で絞ってから本評価する

1候補の正確な評価が高いとき、安い近似で候補を絞り、残った候補だけ正確に調べる方法があります。最初の値を代理評価と呼びます。

1000候補あり、安い評価に1、正確な評価に100の費用がかかるとします。全候補を正確に評価すると10万の費用です。全候補を安く評価して上位20個だけ精査すれば、費用は `1000 + 20 × 100 = 3000` です。ただし、代理評価が本当の最良候補を上位20個に残すとは限りません。

例えば将来の混雑まで計算する代わりに、まず移動距離だけで候補を順位付けすることが考えられます。移動距離は安く比較できますが、近くても混雑する場所を過大評価する可能性があります。

**注意。** この絞り込みは、通常は正解を失わない枝刈りではありません。小さな入力では全候補を本評価し、最良が残る割合と、落としたときの損失を測ります。単に2つの評価の相関が高いだけでは、上位候補の取りこぼしは分かりません。

**練習。** 正確な評価の上位5候補のうち、代理評価の上位20に何個入るかを測る集計を考えてください。残す数Kを増やしたとき、時間と取りこぼしがどう変わるか比較します。

**キットとの対応。** 代理評価による保持に `TopK` を使えます。代理評価と本評価の式は利用者が用意します。

<a id="b18"></a>
## B18. 重み付き抽選で候補の種類を混ぜる

候補A、B、Cを同じ頻度で使う代わりに、相対的な重みを与えて選びます。重み `2, 3, 5` なら、合計10のうちそれぞれ2、3、5を担当し、抽選確率は20%、30%、50%になります。

実装では、0以上合計未満の値を引き、累積和のどの区間に入るかを調べます。重みの絶対値は本質ではありません。`2, 3, 5` と `20, 30, 50` は、理想的な実数計算では同じ確率を表します。

探索では「交換」「挿入」「大きい作り直し」の割合を変える用途に使えます。常に最も良さそうな1種類だけを選ぶと、ほかの種類を試す機会を失います。

**注意。** 重み0の項目は選ばれません。すべて0の場合の扱いは実装によって違うので、必ず確認します。現行の `Random::weighted_index` は空でない配列と正の合計を前提とし、全て0の場合はassertで停止します。各重みを有限・非負にし、有効な候補に正の重みを与えます。

**練習。** 重み `1, 0, 3` で1万回抽選し、各項目の回数を数えてください。期待回数と完全一致しなくてよい理由も説明してください。

**キットとの対応。** [Random::weighted_index(weights)](../../library/random.hpp)。1回の抽選で重み列を走査します。

<a id="b19"></a>
## B19. 候補の得点だけでなく計算費用も見る

1回の試行で大きく改善する近傍でも、その試行に時間がかかりすぎると、時間制限内の最終解では負けることがあります。評価回数を揃えた比較と、実時間を揃えた比較は別です。

例えば近傍Aは1回1マイクロ秒、Bは1回100マイクロ秒かかるとします。同じ時間ならAを約100倍試せます。「Bの方が1回の改善量が10倍」という情報だけでは、Bを優先する根拠として足りません。

一方、改善量を時間で割った値だけでも不十分です。大きい近傍が局所最適を抜け、その後の小さい近傍を有効にすることもあるためです。短期の改善効率と、組合せたときの最終得点を両方調べます。

**注意。** 試行途中で計算費用が変わることがあります。候補数が増えた終盤だけ極端に遅い場合、平均時間では締切超過を予測できません。

**練習。** Aだけ、Bだけ、AとBを混ぜる、の3方式を同じ入力・時間制限で比べる表を作ってください。最終得点以外に、試行数と最長試行時間も記録します。

**キットとの対応。** 全体予算に `Timer`、選択割合に `Random::weighted_index` を使えます。近傍別の回数は `MoveStatistics`、処理時間は [ScopeProfiler](../../library/scope-profiler.hpp) などで記録できます。
