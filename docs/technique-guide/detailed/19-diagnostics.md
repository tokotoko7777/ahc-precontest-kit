## D322. 近傍別受理率

近傍が選ばれた回数、合法だった回数、受理された回数、最良を更新した回数は、それぞれ違う情報です。

受理率90%でも同点移動だけなら得点は伸びません。種類ごとに計測すると、候補生成が悪いのか、温度が合わないのかを切り分けられます。

<a id="example-30423648-06"></a>
### コードでの具体例：提案・採用・best更新を別々に数える

近傍種類ごとの選択数と採用数、全体best更新数をstderrへ出す。

**適用条件・落とし穴。** 採用率だけで有効性を判断せず、無効率とbest寄与も比較する。

**検算と練習。** 選択0回の除算と、stdoutへの診断混入がないことを確認する。

閉路なら、始点だけでなく開始方向まで戻れるかを検査します。開発中に受理直後の検査を入れると、最終出力で壊れているより原因を特定しやすくなります。

<a id="example-31233938-06"></a>
### コードでの具体例：局所更新後に閉路が残っているか検証する

**適用条件・落とし穴。** 複雑な経路差分はスコア一致だけでなく構造条件でも検査する。

**検算と練習。** 短い閉路・交差・盤面端を含むケースで検証を有効にする。

## D324. 未使用処理の識別

ソース内に関数があることと、実際に呼び出されることは別です。入口から分岐と登録表を辿ります。

先のifでx≤16を全て処理した後に、もう一度x≤16の分岐があっても到達しません。未使用の処理を勝因として説明しないための読解です。

<a id="example-34095240-06"></a>
### コードでの具体例：関数の存在と近傍表への登録を分けて読む

押し出し関連の関数が追加されているが、Runの登録表は共通の6近傍のまま。この追加関数を実際に使った最適化とは扱わない。

**適用条件・落とし穴。** 長い競技コードや実験残骸のある提出を読む際に必要。文字列検出だけでは実行経路を特定できない。

**検算と練習。** 定義から呼出箇所まで追い、登録表と到達可能性を照合する。

出典: [AHC013 / 提出 34095240](https://atcoder.jp/contests/ahc013/submissions/34095240) · `transitions / Transition_MoveOutBias` · L2103–L2115, L3331–L3345。 [収録情報](SOURCES.md#submission-34095240)

<a id="example-44783436-07"></a>
### コードでの具体例：先行条件で到達不能になる解法分岐を除く

最初のS<=16で小ノイズを全て処理するため、後続のS<=0や再度S<=16の分岐には到達しない。実際の経路はSQRTとOnePoint。

**適用条件・落とし穴。** 複数の実験解法を残したソースの調査。定義数を採用アルゴリズム数として数えない。

**検算と練習。** 入力の各Sについて通る分岐を手で列挙し、カバレッジと照合する。

## D325. 差分計算の検算

状態ハッシュも差分評価と同じく、完全再計算と一致するか確認します。

XOR型なら古い要素をXORで除き、新しい要素をXORで加えます。交換後の2項だけ加えると、古い寄与が残る可能性があります。疑わしい更新式を検算する観点です。

<a id="example-42958359-05"></a>
### コードでの具体例：ハッシュ更新式は完全再計算と突き合わせる

完全ハッシュは位置と値のXORだが、try_applyでは交換前2項の除去が見当たらず、新2項だけをXORしている。検算assertはコメントアウトされている。

**適用条件・落とし穴。** この式を正しいZobrist差分として移植しない。経路依存のキーになる可能性がある。

**検算と練習。** 同じ盤面へ至る異なる操作列と、hash()の完全再計算値を比較する。

出典: [AHC021 / 提出 42958359](https://atcoder.jp/contests/ahc021/submissions/42958359) · `State::hash / try_apply` · L319–L355, L423–L425。 [収録情報](SOURCES.md#submission-42958359)

## D326. 評価値の型

評価の値域は、通常時の点数だけでなくボーナスや番兵値まで含めて決めます。

2^60の完成ボーナスを持つ値を32ビットintへ入れると、同じ値を保持できません。保存先や比較用の一時変数まで、必要な型が通っているか調べます。

<a id="example-42958359-06"></a>
### コードでの具体例：完了ボーナスを含む評価値の縮小変換を避ける

scoreはunsigned long longで完了時に2^60を加える一方、最良候補のmax変数はint。代入で値域を失う箇所として区別する。

**適用条件・落とし穴。** 大きな番兵値を加える評価設計。最良値も同じ幅の型を使うのが検討点。

**検算と練習。** 完了解を複数含む候補列で選択結果を確認し、縮小変換警告を有効にする。

**適用条件・落とし穴。** 同じマクロ行動に複数の同価経路がある探索。乱数呼出順と入力状態の一致が必要。

## D329. 計算結果の採用確認

重い計算を呼び出していても、その結果が後続の状態へ反映されていなければ最適化として働きません。

改善した配列を返す関数を呼んだ後、古い配列を使い続ける例です。呼出しの有無だけでなく、戻り値から出力までのデータの流れを追います。

<a id="example-60609745-06"></a>
### コードでの具体例：2回目の勾配降下は返り値が寸法へ反映されない

2回目にgradient_descentを呼ぶが、その後はret.0でなくnow_numからfsを更新している。実際に使われるのは1回目とその後の符号方向更新。

**適用条件・落とし穴。** 読解では関数呼出だけで採用された計算と判断しない。改善提案としては不要計算削除か返り値採用を比較する。

**検算と練習。** 各段階の推定配列を記録し、出力寸法に何が反映されたか確認する。

## D330. 実現可能性の段階検査

探索中の安い検査で全部を保証できない場合、最良候補へ詳しい実現可能性検査を行います。

大まかな駅計画は良くても線路へ展開できないことがあります。過去の検証済み候補を残しておけば、失敗時に出力可能な解へ戻せます。

<a id="example-63121685-05"></a>
### コードでの具体例：局所検査を通した最良解も、展開不能なら過去の最良へ戻す

局所変更時は周辺3層などに絞った弱い検査を使い、具体化に失敗した最良候補は履歴から破棄して復帰する。

**適用条件・落とし穴。** 強い検査が高価な抽象探索向け。必ず実行可能な初期解を履歴に保持する。

**検算と練習。** 意図的に展開不能候補を作り、履歴の復帰が安全か試す。

## D331. 多段スコアの二重計上

複数段階の得点を扱うとき、「前段までの和」と「全段の和」を同時に足すと前段が二重になります。

前段10、今段3なら全体13です。全体13へ前段10を足すと23になります。現在候補と新候補が同じ範囲の得点を比較しているか確認します。

<a id="example-69285442-05"></a>
### コードでの具体例：過去段の和が比較側に二度入る箇所を確認する

pre_sumは前段の割当和、best_sumは全段の割当和なのにbestでは両方を足す。一方候補側は目標からpre_sumを引いて解いている。

**適用条件・落とし穴。** 第2段の受理基準に非対称な計上が見える。意図や実測効果は未確認で、再利用前の検証課題として扱う。

**検算と練習。** 前段の和が非ゼロの小例で現在解の誤差とbestを照合する。

## D333. 後処理前の安全な解を保存

操作列を短くする後処理は、正しい完成解を壊す可能性があります。元の列を残してから変換します。

短縮後の列を初期状態から実行し、成功し、かつ本当に短い場合だけ置き換えます。後処理が失敗しても、元の解を出せる構成にします。

<a id="example-77562268-05"></a>
### コードでの具体例：短縮結果が全再生を通らなければ元の操作列へ戻す

探索で得た完成解を保存し、後処理が短くかつ検証成功の場合だけ採用する。

**適用条件・落とし穴。** 複雑な等価変形を追加する際の実装構成。検証器も独立した単純な実行器で確かめたい。

**検算と練習。** 不正な書換候補を混ぜても元の完成解が出るか検査する。

出典: [AHC068 / 提出 77562268](https://atcoder.jp/contests/ahc068/submissions/77562268) · `before_postprocess / p.verify` · L2171–L2187。 [収録情報](SOURCES.md#submission-77562268)

## D334. 最良解の独立した全再生

探索用の差分状態を信じるだけでなく、最後は独立した初期状態から全操作を再生します。

内部では全て処理済みと数えていても、操作列に抜けがあれば再生で見つかります。最良候補が失敗した場合に備え、検証済みの安全な候補も保持します。

<a id="example-79793411-07"></a>
### コードでの具体例：最後に初期盤面から全操作を検証して出力候補を選ぶ

探索用の状態とは別に初期山から全操作を再生し、全て空になるか確認。最良・記録・検証済み安全解を順に選ぶ。

**適用条件・落とし穴。** 複雑な差分操作列探索の仕上げ。safe作成にも失敗する可能性は入力条件と合わせて検査する。

**検算と練習。** 差分状態を故意に壊しても不正列を出さないか試す。

出典: [AHC072 / 提出 79793411](https://atcoder.jp/contests/ahc072/submissions/79793411) · `fullCheck / safe / record` · L2791–L2802, L14414–L14455。 [収録情報](SOURCES.md#submission-79793411)
