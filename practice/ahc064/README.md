# AHC064 練習解答: ブロック移送の差分ビームサーチ

提出するのは [`main.cpp`](./main.cpp) だけです。外部ヘッダやこのリポジトリのライブラリには依存しません。

## 問題を短く整理

10本の出発線にある100両の車両を、10本の待避線も使って並べ直します。目標は、出発線 `r` を先頭から

```text
10*r, 10*r+1, ..., 10*r+9
```

にし、待避線をすべて空にすることです。

- 出発線の末尾から連続した `k` 両を、待避線の先頭へ移せる
- 待避線の先頭から連続した `k` 両を、出発線の末尾へ戻せる
- 出発線の容量は15両、待避線の容量は20両
- 1ターンでは同じ出発線・待避線を2回使えない
- 同時移動 `(i, j)` は、`i` の順と `j` の順が一致しなければならない
- 完成時の得点は `5000 - ターン数`

つまり、まず完成させることが最重要で、その後は複数の移動を安全に同時実行してターン数を減らします。

公式問題: <https://atcoder.jp/contests/ahc064/tasks/ahc064_a>

## 最も簡単なbaseline

0ターンを出力すれば合法です。初期配置のうち、偶然正しい線・位置にある車両だけが得点になります。

```bash
g++ -std=c++17 -O2 -DSIMPLE_BASELINE main.cpp -o baseline
./baseline < in.txt > out.txt
```

## この解法

### 1. 「完成まであとどれくらいか」を隣接関係で測る

目標配置を、次の100個の小さな条件へ分けます。

- 各出発線の先頭が `0, 10, 20, ..., 90` である: 10条件
- `0→1`, `1→2`, ..., `98→99` のうち、同じ目標行に属する2両がこの向きで隣接する: 90条件

離れている2両でも、両方が移動可能な端へ出ていれば小さな罰、列の奥に埋まっていれば大きな罰を与えます。罰が0なら目標配置が完成しています。

公式得点そのものではなく、「次にどのブロックを動かせば目標の鎖がつながるか」を探索へ伝える代理評価です。

### 2. 合法な連続ブロック移動をすべて候補にする

出発線 `i` と待避線 `j` の全100組について、容量を守れるすべての `k` を列挙します。

```text
出発線の末尾 k 両 -> 待避線の先頭
待避線の先頭 k 両 -> 出発線の末尾
```

1両だけでなく、連続する完成済み部分をまとめて運べることが重要です。

### 3. 動かした列に関係する罰だけを再計算する

1回の移動で位置が変わるのは、出発線 `i` と待避線 `j` にある車両だけです。そこで、全100条件を毎回計算し直さず、移動した車両に接する先頭条件・隣接条件だけを更新します。

この差分評価により、各状態から全ブロック長を試しても十分高速に動きます。

### 4. 1ターンの同時移動を小さなDPで選ぶ

各 `(i, j)` について最も良いブロック移動を1個選びます。その後、出発線 `i` を0から9へ見ながら、最後に使った待避線番号だけを覚えるDPを行います。

選ぶ `j` を必ず増加させるので、次の3条件が候補生成の時点で保証されます。

- 同じ出発線を2回使わない
- 同じ待避線を2回使わない
- 移動経路が交差しない

探索結果を後から修理する必要はありません。

### 5. 幅100のビームサーチ

最初の状態から1ターンずつ候補を広げ、代理罰が小さい100状態を残します。

- 初手は80通り、それ以降は各状態から10通り作る
- 固定seedの軽量乱数で候補の重みを少し変え、同じ貪欲手だけに偏らないようにする
- 64 bit hashが同じ状態をまとめ、ビーム幅を重複へ使わない
- 完成した時点でその操作列を返す
- 1.85秒または100ターンで探索を止める

乱数seedは固定なので、同じ実行環境なら基本的に同じ操作列になります。時間打ち切り付近では、CPU負荷によって探索量が変わる場合があります。

## コードを読む順番

1. `main`: 入力、時間制限、探索、出力
2. `State`: 出発線・待避線・代理罰・操作履歴
3. `pair_penalty_with_sizes` と `top_penalty_with_sizes`: 代理評価
4. `single_action_gain`: 1移動の差分評価
5. `select_turn_by_dp`: 非交差な同時移動を選ぶDP
6. `beam_search`: 幅100の探索とhash重複除去
7. `apply_action_to_board`: 公式操作を盤面へ反映

独自の `namespace` は使っていません。補助関数の先頭にある `static` は「このファイルの中だけで使う関数」という指定です。これにより、単純に匿名namespaceを外した場合よりGCCがホット関数を最適化しやすくなります。

```bash
g++ -std=c++17 -O2 -Wall -Wextra -Wshadow -Wconversion -Werror \

./main < in.txt > out.txt
```

```bash

```

## 公式seed 0〜99での検証

通常版と0ターンbaselineを、同じ公式100入力へ1回ずつ実行しました。

| 版 | 合法 | 完成 | 平均得点 | 最小 | 最大 | 合計 | 平均ターン |
|---|---:|---:|---:|---:|---:|---:|---:|
| 0ターンbaseline | 100 / 100 | 0 / 100 | 20.25 | 3 | 50 | 2,025 | 0.00 |
| 差分ビーム | 100 / 100 | 100 / 100 | 4,967.41 | 4,964 | 4,969 | 496,741 | 32.59 |

- 完成版の勝 / 分 / 敗: `100 / 0 / 0`
- 完成版のターン数範囲: `31〜36`
- 100ケースのsolver wall time合計: `129.74`秒、1ケース平均 `1.297`秒
- 観測最大wall time: `4.15`秒。共有実行環境でプロセスが一時停止された値で、探索内部の締切は1.85秒
- 最大RSS: `12,544 KiB`
- strict compile: 通常版・baselineとも警告なし
- AddressSanitizer + UndefinedBehaviorSanitizer: seed 0、3、58、99で異常なし
- sanitizer版の出力も公式visualizerで4ケースすべて合法

sanitizer版は計装で探索が遅くなり、4ケースの得点は `18, 35, 15, 63` でした。これはメモリ安全性と合法性の確認だけに使い、通常版との性能比較には使っていません。

## 既存資産と知識コーパスの扱い

手元に保存していた旧 `main.cpp` を監査し、元の解法を提出用の正本へ整理しました。主な整理は次の3点です。

- 匿名namespaceを、同じ内部リンケージを保つ `static` 補助関数へ置き換えた
- AtCoderの2秒制限へ余裕を持たせるため、内部締切を1.95秒から1.85秒へ変更した
- `SIMPLE_BASELINE` とstrict compile対応を追加した

Knowledge mapから問題構造で検索し、AHC064・AHC021・AHC041・AHC059のReviewだけを参照しました。

- AHC064の確認済みレビュー: ブロック移送、差分評価、候補制限、状態重複除去付きビーム
- AHC021/AHC041からの一般的な観点: 局所差分とhashでビーム幅を有効状態へ使う
- AHC059からの一般的な観点: 交差・入れ子制約を表現の時点で保証する

コーパス内の代表提出Scoreは未照合なので、性能根拠には使っていません。第三者提出コードや長い文章は転記せず、上表はこの `main.cpp` を手元の公式ツールで再実行した結果です。
