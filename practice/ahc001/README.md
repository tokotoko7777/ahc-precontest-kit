# AHC001: 領域再構築の焼きなまし

公式問題: [A - AtCoder Ad](https://atcoder.jp/contests/ahc001/tasks/ahc001_a)

[`main.cpp`](main.cpp) **だけで提出できます**。必要なヘッダは展開済みで、
別ファイル、ローカルinclude、提出前の生成処理は不要です。
編集箇所を読みやすくした原本は
[`ahc001_region_sa.cpp`](../../examples/search/ahc001_region_sa.cpp)です。
CIで原本＋ヘッダと提出用ファイルの完全一致を確認します。

2026-09-19に[5回の改善比較](../../benchmarks/AHC001_FIVE_ROUNDS_REPORT.md)を実施しました。
現在の`main.cpp`は、作業領域再利用・4方向の領域縮小・要求面積を狙う境界移動を採用した版です。
設定固定後の別20ケースは、元の平均985,088,989.80から987,606,315.90へ改善（17勝3敗）。
共通分母の平均比率は99.737940%から99.992420%。以下の古い測定は、当時の版の記録です。

## ライブラリと問題側の境界

| 場所 | 何を書くか・何を返すか |
|---|---|
| `RegionProblem::State` | 要求点を含む非重複の担当領域と、領域ごとの評価cache |
| `Move / propose_move` | 動かす領域、辺、座標、再構築する相手。Stateは変えず、小さな操作情報を返す |
| `quality / score` | 領域の評価値とその合計。大きいほど良い |
| `evaluate_move(state, move, threshold)` | 評価はこの1関数だけ。変更後−変更前の**差分**を返す。不合法・閾値以下と確定したら`nullopt`。仮変更は`pending`へ置く |
| `apply_move` | 採用された`pending`だけStateへ反映する。不採用なら呼ばれない |
| 初期解・最終出力 | 再帰分割で領域を作る／領域内で整数の縦横サイズを選ぶ |
| `TimeBasedAnnealingRunner` | 時間管理、温度、採否、受理閾値、現在解・最良解の保存。問題ごとの編集は不要 |

コードの`TODO(AHC001)`と`TODO:`に、編集する内容と戻り値の意味を書いています。

使うパーツは`BatchedTimer`、`Random`、`AxisAlignedRectangle`、
`largest_empty_rectangle`、`TimeBasedAnnealingRunner`です。
診断時だけ有効になる`ScopeProfiler`も展開済みです。
今回追加した[`largest-empty-rectangle.hpp`](../../library/largest-empty-rectangle.hpp)は、
指定セルを含む最大面積の空き長方形を求めます。座標型はRect側で選べます。

## 解法

1. 最初の約180 msで、多点スタートの再帰分割により1社1領域の初期解を作る。
2. 領域の辺を押し動かし、重なった相手の領域を縮める。相手の要求点を失う操作は棄却する。
3. ときどき1領域、または近い2領域を外して空き長方形として再構築する。
   2領域では、要求点を分ける境界を3本試し、両側で再配置する。
4. 時間ベースの焼きなまし後、最良解からほぼ山登りで仕上げる。
5. 各領域の内部で、公式得点が最大になる整数の幅・高さを選んで出力する。

担当領域は要求面積より大きくても構いません。探索中は
`1 - (1 - min(1, 領域面積 / 要求面積))²`を代理評価にします。
余分な空間を持ったまま近傍探索し、出力時だけ最適な広告サイズへ縮めます。
**整数サイズによる丸めがあるため、代理評価と公式得点は完全には一致しません。**

境界を押す近傍では、動かした領域の利得から、相手の縮小損失を順に引きます。
残りの変化はすべて非正なので、途中の差分が受理閾値以下ならそこで棄却できます。
これは推測による枝刈りではありません。1・2領域の再構築では、この早期打ち切りは使いません。

通常は全体4,750 msを目安に探索し、公式5秒制限へ余裕を残します。
時計は間引いて確認するため、提出環境でのTLEを保証するものではありません。
`-DAHC001_TIME_LIMIT_MS=...`で変更できます。
`-DAHC001_ITERATIONS=100`は短時間の整合性検査用で、得点比較の設定ではありません。

### 前計算・スコア途中打ち切り・処理別計測（任意）

前計算と途中打ち切りを独立にON/OFFできます。提出用`main.cpp`でも同じ設定です。

| コンパイル設定 | 意味 | 既定 |
|---|---|---|
| `-DAHC001_PRECOMPUTE_THRESHOLD=0` または `1` | 受理判定の対数表をOFF／ON | OFF |
| `-DAHC001_SCORE_EARLY_STOP=0` または `1` | 差分スコアの途中打ち切りをOFF／ON | ON |
| `-DAHC001_THRESHOLD_TABLE_SIZE=4096` | ON時の表サイズ | ONなら4096 |

従来の表サイズ指定だけでもONになります。明示的な`PRECOMPUTE_THRESHOLD=0`があれば
サイズ指定より優先してOFFにします。前計算OFFでも受理閾値は毎回logで作るため、
途中打ち切りを使えます。途中打ち切りOFFでは同じ評価関数へ`-∞`を渡して全差分を求め、
不合法手は`nullopt`で棄却します。通常評価用の別関数を書く必要はありません。
ON/OFFで受理乱数の消費方法は同じです。時間ベースでは試行回数などが変わるので、
同じseedでも最終スコアの一致を意味しません。

```sh
g++ -std=c++17 -O2 -DNDEBUG -DAHC001_PRECOMPUTE_THRESHOLD=0 \
  -DAHC001_SCORE_EARLY_STOP=1 practice/ahc001/main.cpp -o build/ahc001
```

通常の受理確率は近似せず、境界に近い場合だけ元のlog計算へ戻します。
詳細は[`MARATHON_LIBRARY_REVIEW.md`](../../MARATHON_LIBRARY_REVIEW.md)を参照してください。

`-DAHC_ENABLE_PROFILING`では、stderrへ評価全体と再構築の回数・合計msを出します。
再構築は評価全体に含まれるため、両方の時間を足さないでください。
通常ビルドは計測用の時計取得・記録・出力をしません。

## 1位との差の記録方法

1位hakomoさんの参考値を[`reference-scores.json`](reference-scores.json)へ保存しました。

| 参考記録 | ケース数 | 合計score | 1ケース平均 |
|---|---:|---:|---:|
| 暫定 A | 50 | 49,697,919,919 | 993,958,398.38 |
| 最終システムテスト | 1,000 | 993,823,071,683 | 993,823,071.683 |

出典は[公式順位表](https://atcoder.jp/contests/ahc001/standings)と
[暫定提出](https://atcoder.jp/contests/ahc001/submissions/20926292)・
[最終採点記録](https://atcoder.jp/contests/ahc001/submissions/77738201)の
2026-07-24保存済みメタデータです。順位表JSONのScoreは100で割り、
表示された提出得点と対応させています。
**2026-09-15の再確認ではログイン要求・HTTP 403があり、正確な得点の現行ページでの
再検証はできていません。保存済み公式データによる参考値であり、1位コードを実行して
再現した値ではありません。**

比較scriptは次を出します。

- 平均点差: `1位の平均 − この版の平均`。正ならその分だけ不足。
- 1位比: `100 × この版の平均 / 1位の平均`。
- 満点からの損失倍率: `(1e9 − この版の平均) / (1e9 − 1位の平均)`。
  1位比が99%以上でも、残る損失がかなり違うことを見落とさないための補助指標。

10ケースや100ケースの平均と1位の1,000ケース平均は、**入力集合が違う参考比較**です。
順位相当・全ケースでの差・統計的な有意差は主張しません。
公開システムseed全1,000件を同じ版で測れば入力集合は揃いますが、
それでも実行環境が違うローカル測定であり、公式順位にはなりません。

## 自分のPCでベンチマークする

[公式ツールzip](https://img.atcoder.jp/ahc001/ded8fd3366b4ff0b0d7d053f553cdb84.zip)を展開し、
`tools`で`cargo build --release --bins`を実行します。
[公式システムseed](https://img.atcoder.jp/ahc001/seeds.zip)は別ディレクトリへ展開します。
付属の開発用`tools/seeds.txt`と取り違えないでください。

```sh
# 開発用10ケースで旧practiceと比較
python3 benchmarks/ahc001_official_benchmark.py \
  --tools /path/to/tools --seeds /path/to/tools/seeds.txt \
  --cases 10 --output build/ahc001-development.csv

# 公開システムseed 1,000件を提出用main.cppで測る（逐次実行で約80分）
python3 benchmarks/ahc001_official_benchmark.py \
  --tools /path/to/tools --seeds /path/to/system/seeds.txt \
  --suite system --cases 1000 --skip-reference \
  --solver practice/ahc001/main.cpp --output build/ahc001-system.csv

python3 benchmarks/ahc001_gap_report.py \
  --csv build/ahc001-system.csv --suite system
```

システムseedは1,000行と公式MD5
`8fc1ce3f4beabac6abc1bdb4206d7f7e`をscriptが検査します。
`--cases 100`など部分実行なら、差の表示は参考扱いになります。
出力CSVを上書きしないので、再測定時は新しい名前を指定してください。
各行へ入力・出力・sourceのhash、seed、得点、実時間、5秒超過フラグを残します。
スコア測定中は、他の重い処理を同時に走らせないことを推奨します。

対数区間表の有無だけを比べる場合は、同じsolverを2通りでコンパイルします。
このモードの`reference`は古いpracticeではなく、**現在のsolverの表なし版**です。
`reference_commit`は空、`source_sha256`は共通、
`threshold_table_size`が4096と0で区別できます。

```sh
python3 benchmarks/ahc001_official_benchmark.py \
  --tools /path/to/tools --seeds /path/to/system/seeds.txt \
  --suite system --first-case 100 --cases 20 \
  --threshold-table-size 4096 --compare-threshold-table \
  --output build/ahc001-table-comparison.csv
```

`--score-early-stop 0`を加えると途中打ち切りOFF、`1`ならON（既定）です。
`--compare-threshold-table`では両方の現行solverへ同じ打ち切り設定を渡します。
旧commitとの比較では設定は現行solverだけに適用し、旧版の`score_early_stop`列は空欄です。
4通りの少数ケース動作確認と単一評価関数への移行後の再確認は
[生データの説明](../../benchmarks/results/README.md)を参照してください。

## 検証・残る課題

- 最大空き長方形: 小盤面1,200件を全列挙と照合。障害物同士の重なりも含む。
- 領域内サイズ選択: 小さい幅・高さ・要求面積の全候補と照合。
- 近傍: 差分値と全再計算、採用後の合法性、閾値版の棄却条件を照合。
- 提出用1ファイルと原本・ライブラリの展開一致をCIで検査。
- 2領域の切断は3候補のみ。共同配置の厳密な最適化ではない。
- 最大空き長方形は障害物M個でO(M² + M log M)。頻度を抑えて使っている。
- 領域代理評価、近傍比率、段階的な温度設定には改良余地がある。
- [hakomoさんの優勝解説](https://hakomof.hatenablog.com/entry/2021/03/14/202411)と
  [TERRYさんの参加記](https://blog.terry-u16.net/entry/ahc001)を着想に使用。
  第三者の提出コードの移植ではなく、このkitの初期解とRunner上の独自実装。
- AHC069の解答・ベンチマークとは無関係。
