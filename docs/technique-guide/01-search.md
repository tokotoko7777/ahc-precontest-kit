# 1. 探索の組み立て方

[目次へ](README.md) · [次：焼きなましと温度](02-annealing.md)

探索とは、候補となる答えを作り、評価し、限られた時間でより良い答えへ移っていく処理です。速い乱数や難しい近傍を導入する前に、「何を答えとして持つか」を決める必要があります。

<a id="b01"></a>
## B01. 状態・目的・制約を分けて考える

**状態**は探索中に持っている答えの表現です。**目的関数**はその良さを数値にする関数、**制約**はその答えを提出してよいかを決める条件です。

例えば、いくつかの地点を訪問する順番を探すなら、状態は地点IDの配列です。目的を移動距離の最小化とすると、目的関数は連続する地点間の距離の合計になります。「すべての地点をちょうど1回ずつ訪問する」は制約です。距離が短くても地点を1つ落とした配列は、良い答えにはなりません。

この3つを分けると、バグの切り分けができます。順列が壊れているなら状態更新、距離が違うなら評価、提出形式が違うなら出力を調べればよくなります。

**実装の形。** 最初は `valid(state)` と `evaluate(state)` を別に用意します。更新のたびに全部を検査すると遅くても、開発中の正解判定器として残す価値があります。

**注意。** 探索用の評価に罰点を足した場合、それは公式の得点と別の値です。どちらを記録しているか、変数名とログで区別します。

**練習。** 「仕事を日付に割り当てる」問題について、状態・目的・制約を1つずつ書いてください。次に、制約だけが壊れた状態と、制約は満たすが悪い状態を作ってください。

**キットとの対応。** 問題固有の状態と評価関数は利用者が作ります。キットはそれらを動かす乱数・受理・時間管理などを提供します。

<a id="b02"></a>
## B02. 現在解と最良解を別々に持つ

探索が今いる場所を現在解、これまでに見つけた最も良い答えを最良解と呼びます。途中で悪い場所へ移る探索では、この2つは一致しません。

最大化問題で得点が `100 → 105 → 102` と変化したとします。最後の現在解は102点ですが、出力したいのは途中の105点の状態です。最良スコアだけを保存し、対応する状態を保存し忘れると、105という値から答えを復元できません。

更新の順序は「候補を採用する」「現在解を更新する」「現在解が最良を超えたら最良解も更新する」です。終了時は最良解を出力します。

**注意。** 最良解に現在解への参照だけを保存すると、その後の変更で両方が変わることがあります。独立したコピーか、確実に復元できる履歴が必要です。巨大な状態ではコピーが高価なので、本当に最良が更新されたときだけ保存します。

**練習。** 現在解が `8 → 11 → 9 → 10` と動いたとき、各時点の最良値を書いてください。さらに、状態だけ保存して最良スコアを更新し忘れたら何が起こるか考えてください。

**キットとの対応。** [BestKeeper](../../library/best-keeper.hpp) が最良スコアと対応する状態を保持します。現在解は探索側で別に持ちます。

<a id="b03"></a>
## B03. 局所改善とリスタートの役割を分ける

局所改善は、今の答えの近くを調べて良くしていく方法です。交換できる2要素を全部試しても改善しない状態があっても、離れた場所に良い答えがないとは限りません。その状態は、使っている近傍に対する局所最適です。

リスタートは初期解を変えて探索をやり直します。1回目と違う領域から始めることで、別の局所最適へ到達する可能性を作ります。同じ初期解、同じ乱数列、同じ回数で再実行するだけでは、原則として同じ道を辿ります。

例えば総予算が1万回の評価なら、1つの初期解に1万回使う方法と、10個の初期解に1000回ずつ使う方法を比較できます。前者は1つの領域を深く掘り、後者はいろいろな領域を試します。

**注意。** 再初期化が高価な場合、短いリスタートを増やすと準備だけで時間を使います。また、各回の最後の解ではなく、全リスタートを通じた最良解を保持します。

**練習。** 全体で1000回評価でき、初期化が評価100回分の費用を持つ場合、10回のリスタートでは改善に何回分の余裕が残るか計算してください。

**キットとの対応。** 外側のループと初期解生成は自分で作り、全体の `Timer` を共有します。

<a id="b04"></a>
## B04. 小さい近傍と大きい近傍を使い分ける

近傍とは、現在解から1回の操作で移れる候補の集合です。順列の2要素交換なら変更は小さく、区間全体の作り直しなら変更は大きくなります。

小さい変更は評価を安くしやすく、良い解を少しずつ磨くのに向いています。一方、複数要素が相互に邪魔をしている場合、1要素ずつ動かしても改善できません。大きい変更はその組合せをまとめて変える機会を作ります。

例えば2つの仕事を別の日へ動かしたいのに、どちらの移動先にも空きがないとします。片方だけの移動は失敗しますが、2つの仕事の日付を交換すれば制約を満たせるかもしれません。「要素を1つ選ぶ」か「交換ペアを選ぶ」かで、到達できる状態が変わります。

**注意。** 大きい近傍が必ず良いとは限りません。候補生成が遅くなったり、ほとんど無効になったりすることがあります。近傍ごとに、試行数・有効候補数・採用数・計算時間を記録します。

**練習。** 順列に対して、交換・1要素の挿入・区間反転の3つを書き出し、それぞれが1回で変えられる構造の違いを説明してください。

**キットとの対応。** 近傍自体は問題固有です。近傍の種類を重み付きで選ぶ部分に [Random::weighted_index](../../library/random.hpp) を使えます。

<a id="b05"></a>
## B05. 制約を守る変更と、壊してから直す変更

制約を常に守る方法では、どの候補へ移っても提出可能な状態を保ちます。順列の2要素交換が典型です。要素の種類と個数は変わりません。

別の方法として、一度制約を壊し、その後で修復する設計もあります。例えば容量いっぱいの箱に荷物を入れ替えるとき、先にいくつか取り出して空きを作り、入れ直すことを考えます。修復が成功すれば、単独移動では到達できなかった状態へ進めます。

どちらを使うかは、制約を守る候補を安く作れるか、壊れた状態を確実に直せるかで決まります。修復失敗に備え、元の状態へ戻る経路を持たせます。

**注意。** 罰点を大きくしただけでは、探索終了時に制約違反が消える保証はありません。最良の実行可能解を別に保存し、出力前に検査する設計が必要です。

**練習。** 容量10の箱が2つあり、荷物が `6, 4, 5, 5` のとき、許される状態を2つ書いてください。単独移動と交換で移れるかを比較してください。

**キットとの対応。** 配列への試行と修復を取り消す処理に [RollbackArray<T>](../../library/rollback-array.hpp) を使えます。制約検査そのものは利用者が定義します。
