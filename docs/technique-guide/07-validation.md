# 7. 検証と実験

[目次へ](README.md) · [前：時間予算](06-time.md)

実装の正しさと得点の良さは、別々に確認します。まず状態と出力が正しいことを確かめ、その後で、変更前より良いかを実験します。

<a id="b28"></a>
## B28. 1つの変更を同じ条件で比べる

温度・近傍・評価関数を一度に変えて得点が上がっても、何が効いたか分かりません。まず基準となる版を保存し、1つずつ変えて比較します。

例えば「時計確認を毎回から256回ごとへ変える」なら、入力・seed・時間予算・コンパイル条件を揃えます。反復回数が増え、最終得点が変わったかを見れば、費用を減らした効果を追いやすくなります。

実験記録には、コードの版、入力ID、seed、設定値、得点、実行時間、制約違反の有無を残します。結果だけ保存しても、どの条件だったか分からなくなれば比較に使えません。

**注意。** 開発に使った少数入力だけで設定を調整し続けると、その入力群に合いすぎることがあります。調整に使わない確認用の入力も残しておきます。

**練習。** 開始温度だけを変更する比較表の列を設計してください。温度以外で固定すべき条件も書いてください。

**キットとの対応。** 乱数のseed、タイマーの制限値、焼きなましの開始・終了温度を、実行条件として明示します。記録する項目の例は [実問題ベンチマーク](../../REAL_PROBLEM_BENCHMARKS.md) を参照してください。

<a id="b29"></a>
## B29. 複数seedで揺れを測る

乱択探索では、同じ入力でもseedによって結果が変わります。1回だけ良かった結果を採用理由にすると、たまたま良い乱数列だった可能性を除けません。

変更前後で同じ入力と複数のseedを使い、組ごとの得点差を集計します。多くの組で少しずつ良くなるのか、一部の大勝ちが平均を押し上げているのかを確認します。

**注意。** 同じseedを渡しても、2つの実装が同じ候補列を使うとは限りません。乱数の呼び出し回数が変われば、その後の列の対応が崩れます。「同じseedを使った比較」と「同じ候補列を使った比較」は区別します。

また、固定seedの集合だけを繰り返し見て調整すると、その集合への過適合が起こり得ます。最後に別のseedでも確認します。

**練習。** 5つのseedでの得点差が `+1, +2, +1, +2, -20` の場合、平均だけでなく、勝った回数と最悪の悪化量も求めてください。

**キットとの対応。** `Random(seed)` と `SimulatedAnnealing(start_temperature, end_temperature, seed)`。それぞれが別の乱数器を持つため、両方のseedを記録します。

<a id="b30"></a>
## B30. 平均だけでなく失敗と裾を見る

平均得点が上がっても、時間超過や無効出力が増えているなら、その変更には実用上の問題があります。得点・実行時間・失敗を別々に集計します。

例えば平均実行時間が1.5秒でも、100入力中1件が3秒なら、2秒制限ではその入力を処理できません。平均とともに、中央値、遅い側の分位点、最大値、失敗件数を見ます。分位点は、結果を順に並べてどの位置を見るかを決めた値です。

得点も同様です。複数の入力タイプがあるなら、タイプ別に比べると、特定のタイプだけ悪くなったことに気づけます。

**注意。** 入力ごとに得点の尺度が大きく違う場合、素点をそのまま平均すると、大きい数字が出る入力に支配されます。差分、比率、公式の集計方式など、比較目的に合う尺度を選びます。比率を使う場合は0や負の基準値の扱いを決めます。

**練習。** 99入力が0.9秒、1入力が3秒の実行時間について、平均と最大を計算し、平均だけでは見えない問題を説明してください。

**キットとの対応。** 実行時間の取得は `Timer` でできます。入力群の集計と公式の出力検査は別に行います。

<a id="b31"></a>
## B31. 小さい入力で不変条件を繰り返し調べる

不変条件とは、処理が正しく動く間ずっと成り立つべき性質です。順列なら要素の重複がないこと、割当てなら各要素が所属先を1つ持つこと、差分更新なら保存した評価値と全再計算が一致することなどがあります。

小さな入力では、遅い検査でも毎回実行できます。ランダムな変更を何度も試し、採用と取消しの両方を混ぜ、条件が初めて壊れる瞬間を見つけます。

不具合が出たら入力と操作列を保存し、不要な操作を減らして最小の再現例を作ります。1000操作目で壊れた現象が、「同じ変数を2回更新してから取消す」だけで再現することもあります。

**注意。** 成功例だけを増やしても境界の不具合は見つかりません。空集合、1要素、同じ要素の再選択、重みがすべて0、ログの入れ子、容量の境界などを直接作って調べます。

**練習。** Top-Kについて「保持数がKを超えない」「保持中のどの要素も保持列の末尾より悪くない」「全候補を並べ替えた上位Kと一致する」の3条件を、小さな列で確かめてください。

**キットとの対応。** [部品のテスト](../../tests/parts_test.cpp)を入口に、問題固有の不変条件を追加します。

<a id="b32"></a>
## B32. 症状から、次に測るものを決める

得点が伸びない原因は1つとは限りません。すぐに近傍を複雑にする前に、どこで仕事を失っているか測ります。

| 症状 | 最初に調べるもの | 次の対応候補 |
|---|---|---|
| 候補のほとんどが無効 | 有効候補率、無効になる制約 | 制約を守る候補生成、状態表現の見直し |
| 悪化をほぼ全部受理 | 悪化量と温度、同点を除いた受理率 | 温度の尺度と冷却の確認 |
| 序盤から動かない | 得点差の符号、温度、近傍の到達範囲 | 受理判定の検算、近傍の変更 |
| 時間は使うが試行が少ない | 候補生成・コピー・評価・時計の費用 | 最も重い部分から削減 |
| 長く動かすほど評価が怪しい | 全再計算との差、取消し後の状態 | 差分式と補助データの復元を検査 |
| 終了間際だけ時間超過 | 最長試行、復元・出力時間、確認間隔 | 終了余白と内側ループの締切確認 |

測定は「次に何を変えるか」を決めるために行います。ログを大量に出しても、原因に対応する値がなければ判断できません。ログ出力自体の時間も増えるため、開発用の集計と提出時の出力を分けます。

**練習。** 自分の探索で最も困っている症状を1つ選び、原因の仮説を2つ立ててください。その2つを区別するために必要な計測値を1つずつ挙げます。

**キットとの対応。** タイマー・乱数・受理関数・ログなど、各部品の境界で値を数えると、問題箇所を絞りやすくなります。
